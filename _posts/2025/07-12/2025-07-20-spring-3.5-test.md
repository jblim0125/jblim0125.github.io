## Spring Boot 애플리케이션 테스트

Spring Boot 애플리케이션은 기본적으로 Spring ApplicationContext이므로, 일반적인 Spring 컨텍스트 테스트와 크게 다르지 않습니다.

외부 프로퍼티, 로깅 등 Spring Boot의 다양한 기능은 SpringApplication을 통해 컨텍스트를 생성할 때만 기본적으로 적용됩니다.  
Spring Boot는 `@SpringBootTest` 어노테이션을 제공하며, Spring Boot의 기능이 필요한 경우 표준 spring-test의 `@ContextConfiguration` 대신 사용할 수 있습니다.  
이 어노테이션은 테스트에서 ApplicationContext를 SpringApplication을 통해 생성합니다.  
또한, `@SpringBootTest` 외에도 애플리케이션의 특정 부분만 테스트할 수 있는 다양한 어노테이션이 제공됩니다.

JUnit 4를 사용하는 경우, 반드시 테스트 클래스에 `@RunWith(SpringRunner.class)`를 추가해야 어노테이션이 정상적으로 동작합니다.  
JUnit 5를 사용하는 경우에는 `@SpringBootTest` 및 기타 테스트 어노테이션에 이미 `@ExtendWith(SpringExtension.class)`가 포함되어 있으므로 별도로 추가할 필요가 없습니다.

기본적으로 `@SpringBootTest`는 서버를 시작하지 않습니다.  
테스트 실행 방식을 세분화하려면 `webEnvironment` 속성을 사용할 수 있습니다:

- **MOCK(기본값)** : 웹 ApplicationContext를 로드하고, 모의 웹 환경을 제공합니다. 내장 서버는 시작되지 않습니다. 웹 환경이 없으면 일반 ApplicationContext로 대체됩니다. `@AutoConfigureMockMvc` 또는 `@AutoConfigureWebTestClient`와 함께 사용하여 웹 애플리케이션의 모의 테스트가 가능합니다.
- **RANDOM_PORT** : 실제 웹 환경을 제공하며, 내장 서버가 랜덤 포트로 시작됩니다.
- **DEFINED_PORT** : 실제 웹 환경을 제공하며, 내장 서버가 지정된 포트(설정값 또는 기본 8080)로 시작됩니다.
- **NONE** : SpringApplication을 사용해 ApplicationContext만 로드하며, 웹 환경은 제공하지 않습니다.

테스트에 `@Transactional`을 사용하면 각 테스트 메서드가 끝날 때마다 트랜잭션이 롤백됩니다.  
하지만 `RANDOM_PORT` 또는 `DEFINED_PORT`를 사용할 경우, HTTP 클라이언트와 서버가 별도 스레드와 트랜잭션에서 동작하므로 서버에서 시작된 트랜잭션은 롤백되지 않습니다.

`@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)`를 사용할 때, 관리용 서버가 별도의 랜덤 포트로 시작될 수 있습니다.

### 웹 애플리케이션 타입 감지

Spring MVC가 있으면 일반 MVC 기반 컨텍스트가 설정되고, Spring WebFlux만 있으면 WebFlux 기반 컨텍스트가 설정됩니다.  
둘 다 있으면 Spring MVC가 우선 적용됩니다.  
반응형 웹 애플리케이션을 테스트하려면 `spring.main.web-application-type` 속성을 지정해야 합니다.

```java
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest(properties = "spring.main.web-application-type=reactive")
class MyWebFluxTests {
    // ...
}
```

### 테스트 설정 감지

Spring Test Framework에 익숙하다면, `@ContextConfiguration(classes=...)`로 어떤 설정을 로드할지 지정하는 경우가 많습니다.  
Spring Boot에서는 보통 필요하지 않습니다.  
Spring Boot의 `@*Test` 어노테이션은 명시적으로 설정을 지정하지 않으면, 기본 설정을 자동으로 검색합니다.

검색 알고리즘은 테스트가 포함된 패키지에서 시작해, `@SpringBootApplication` 또는 `@SpringBootConfiguration`이 붙은 클래스를 찾을 때까지 상위 패키지로 올라갑니다.  
일반적으로 프로젝트 구조가 잘 되어 있다면, 메인 설정을 자동으로 찾습니다.

애플리케이션의 특정 부분만 테스트하는 어노테이션을 사용할 때는, 메인 클래스에 특정 영역의 설정을 추가하지 않는 것이 좋습니다.

`@SpringBootApplication`의 컴포넌트 스캔 설정에는 슬라이싱 테스트를 위한 exclude 필터가 포함되어 있습니다.  
직접 `@ComponentScan`을 사용하면 이 필터가 비활성화되므로, 슬라이싱 테스트를 할 때는 필터를 다시 정의해야 합니다.

기본 설정을 커스터마이즈하려면, 중첩된 `@TestConfiguration` 클래스를 사용할 수 있습니다.  
중첩 `@Configuration`은 기본 설정을 대체하지만, `@TestConfiguration`은 기본 설정에 추가됩니다.

Spring의 테스트 프레임워크는 테스트 간에 ApplicationContext를 캐싱합니다.  
따라서 동일한 설정을 공유하는 테스트는 컨텍스트 로딩이 한 번만 발생하므로, 테스트 속도가 빨라집니다.

### 테스트 설정의 메인 메서드 사용

일반적으로 `@SpringBootTest`가 자동으로 찾는 테스트 설정 클래스는 애플리케이션의 메인 `@SpringBootApplication` 클래스입니다.  
대부분의 잘 구조화된 애플리케이션에서는 이 설정 클래스에 애플리케이션을 실행하는 메인 메서드도 포함되어 있습니다.

예를 들어, 아래는 일반적인 Spring Boot 애플리케이션의 코드 패턴입니다.

```java
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }

}
```

위 예제에서 메인 메서드는 단순히 `SpringApplication.run()`을 호출하는 역할만 합니다.  
하지만, 메인 메서드에서 커스텀 설정을 적용한 뒤 `SpringApplication.run()`을 호출하는 것도 가능합니다.

예를 들어, 아래는 배너 모드를 변경하고 추가 프로파일을 설정하는 예시입니다.

```java
import org.springframework.boot.Banner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication application = new SpringApplication(MyApplication.class);
        application.setBannerMode(Banner.Mode.OFF);
        application.setAdditionalProfiles("myprofile");
        application.run(args);
    }

}
```

메인 메서드에서의 커스텀 설정은 ApplicationContext에 영향을 줄 수 있으므로, 테스트에서도 메인 메서드를 사용해 ApplicationContext를 생성하고 싶을 수 있습니다.  
기본적으로 `@SpringBootTest`는 메인 메서드를 호출하지 않고, 클래스 자체를 사용해 ApplicationContext를 생성합니다.

이 동작을 변경하려면, `@SpringBootTest`의 `useMainMethod` 속성을 `SpringBootTest.UseMainMethod.ALWAYS` 또는 `SpringBootTest.UseMainMethod.WHEN_AVAILABLE`로 지정할 수 있습니다.  
`ALWAYS`로 설정하면 메인 메서드가 없을 경우 테스트가 실패합니다.  
`WHEN_AVAILABLE`로 설정하면 메인 메서드가 있으면 사용하고, 없으면 기본 로딩 방식을 사용합니다.

예를 들어, 아래 테스트는 ApplicationContext를 생성할 때 `MyApplication`의 메인 메서드를 호출합니다.  
메인 메서드에서 추가 프로파일을 설정했다면, ApplicationContext가 시작될 때 해당 프로파일이 활성화됩니다.

```java
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.context.SpringBootTest.UseMainMethod;

@SpringBootTest(useMainMethod = UseMainMethod.ALWAYS)
class MyApplicationTests {

    @Test
    void exampleTest() {
        // ...
    }

}
``ㅓ

### Testing With a Running Server

전체 서버를 실행해야 하는 경우, 랜덤 포트를 사용하는 것을 권장합니다.  
`@SpringBootTest(webEnvironment=WebEnvironment.RANDOM_PORT)`를 사용하면, 테스트가 실행될 때마다 사용 가능한 포트가 랜덤하게 선택됩니다.

`@LocalServerPort` 어노테이션을 사용하면 실제로 사용된 포트를 테스트에 주입할 수 있습니다.  
서버에 REST 호출이 필요한 테스트에서는 `WebTestClient`를 자동 주입하여 사용할 수 있습니다.  
`WebTestClient`는 실행 중인 서버의 상대 링크를 자동으로 처리하며, 응답 검증을 위한 전용 API도 제공합니다. 아래는 예시입니다.

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.context.SpringBootTest.WebEnvironment;
import org.springframework.test.web.reactive.server.WebTestClient;

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class MyRandomPortWebTestClientTests {

    @Test
    void exampleTest(@Autowired WebTestClient webClient) {
        webClient
            .get().uri("/")
            .exchange()
            .expectStatus().isOk()
            .expectBody(String.class).isEqualTo("Hello World");
    }

}
```

`WebTestClient`는 모의 환경에서도 사용할 수 있습니다.  
이 경우 테스트 클래스에 `@AutoConfigureWebTestClient`를 추가하면 서버를 실행하지 않고도 테스트가 가능합니다.  
이 설정은 `spring-webflux`가 클래스패스에 있어야 동작합니다.  
만약 webflux를 추가할 수 없다면, Spring Boot에서는 `TestRestTemplate`도 제공합니다.

```java
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.context.SpringBootTest.WebEnvironment;
import org.springframework.boot.test.web.client.TestRestTemplate;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class MyRandomPortTestRestTemplateTests {

    @Test
    void exampleTest(@Autowired TestRestTemplate restTemplate) {
        String body = restTemplate.getForObject("/", String.class);
        assertThat(body).isEqualTo("Hello World");
    }

}
```

#### WebTestClient 커스터마이즈

`WebTestClient` 빈을 커스터마이즈하려면, `WebTestClientBuilderCustomizer` 빈을 설정하면 됩니다.  
이 빈은 `WebTestClient.Builder`에 대해 호출되어 커스터마이즈를 적용합니다.

#### JMX 사용

테스트 컨텍스트 프레임워크가 컨텍스트를 캐싱하므로, 동일한 컴포넌트가 같은 도메인에 등록되는 것을 방지하기 위해 JMX는 기본적으로 비활성화되어 있습니다.  
테스트에서 `MBeanServer`에 접근해야 한다면, 컨텍스트를 더럽게(mark dirty) 처리하는 것이 좋습니다.

```java
import javax.management.MBeanServer;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.annotation.DirtiesContext;
import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(properties = "spring.jmx.enabled=true")
@DirtiesContext
class MyJmxTests {

    @Autowired
    private MBeanServer mBeanServer;

    @Test
    void exampleTest() {
        assertThat(this.mBeanServer.getDomains()).contains("java.lang");
        // ...
    }

}
```

#### Observation 사용하기

슬라이스 테스트에 `@AutoConfigureObservability` 애노테이션을 추가하면 `ObservationRegistry`가 자동 설정됩니다.

#### Metrics 사용하기

@SpringBootTest를 사용할 경우, 클래스패스와 상관없이 메모리 기반이 아닌 미터 레지스트리들은 자동 설정되지 않습니다.

통합 테스트에서 메트릭 데이터를 외부 백엔드로 전송해야 한다면, @AutoConfigureObservability 애노테이션을 추가하세요.

슬라이스 테스트에서 @AutoConfigureObservability를 사용하면, 메모리 기반의 MeterRegistry가 자동 설정됩니다. 하지만 슬라이스 테스트에서의 데이터 내보내기는 지원되지 않습니다.

#### Tracing 사용하기

@SpringBootTest를 사용할 경우, 클래스패스와 상관없이 데이터를 보고하는 트레이싱 구성 요소는 자동 설정되지 않습니다.

통합 테스트에서 해당 구성 요소가 필요하다면 @AutoConfigureObservability 애노테이션을 사용하세요.

직접 구현한 리포팅 구성 요소(예: 커스텀 SpanExporter 또는 brave.handler.SpanHandler)가 테스트 중에 활성화되지 않기를 원한다면, @ConditionalOnEnabledTracing 애노테이션을 사용해 비활성화할 수 있습니다.

슬라이스 테스트에서 @AutoConfigureObservability를 사용하면, 동작하지 않는(no-op) Tracer가 자동 설정됩니다. 마찬가지로 슬라이스 테스트에서는 데이터 내보내기가 지원되지 않습니다.

#### Bean Mock 및 Spy 처리

테스트 중에는 애플리케이션 컨텍스트 내의 특정 구성 요소를 목(Mock) 처리해야 할 수 있습니다. 예를 들어, 개발 중에는 사용할 수 없는 원격 서비스의 파사드가 있을 수 있습니다. 또는 실제 환경에서 트리거하기 어려운 실패 상황을 시뮬레이션하고자 할 수도 있습니다.

Spring Framework는 @MockitoBean 애노테이션을 제공하여 ApplicationContext 내에서 Mockito 목을 정의할 수 있습니다. 또한 @MockitoSpyBean을 사용하면 스파이도 정의할 수 있습니다. 자세한 내용은 Spring Framework 문서를 참조하세요.

#### Auto-configured Tests

Spring Boot의 자동 구성 시스템은 애플리케이션에는 잘 작동하지만, 테스트에는 너무 과할 수 있습니다. 따라서 테스트하고자 하는 애플리케이션의 일부분(“슬라이스”)만 로드하는 것이 도움이 됩니다.

예를 들어, Spring MVC 컨트롤러가 URL을 올바르게 매핑하는지를 테스트하고 싶은데, 이 테스트에 DB 호출은 포함시키고 싶지 않을 수 있습니다. 혹은 JPA 엔티티를 테스트하고 싶을 때는 웹 레이어를 제외하고 테스트할 수 있습니다.

spring-boot-test-autoconfigure 모듈은 이런 “슬라이스” 테스트를 위해 여러 애노테이션을 제공합니다. 각각은 @...Test 애노테이션과 하나 이상의 @AutoConfigure... 애노테이션을 사용하여 필요한 자동 설정만 로드합니다.

각 슬라이스는 적절한 컴포넌트만 스캔하며 제한된 자동 구성 클래스만 로드합니다. 특정 자동 구성을 제외하고 싶다면 대부분의 @...Test 애노테이션에 있는 excludeAutoConfiguration 속성을 사용하거나, @ImportAutoConfiguration#exclude를 활용할 수 있습니다.

여러 개의 @...Test 애노테이션을 하나의 테스트에 함께 사용하는 것은 지원되지 않습니다. 여러 슬라이스가 필요한 경우, 하나의 @...Test만 사용하고, 나머지 슬라이스의 @AutoConfigure... 애노테이션을 수동으로 포함시키면 됩니다.

slicing이 필요 없고, 일부 테스트 관련 자동 구성만 활용하고 싶다면 @SpringBootTest와 @AutoConfigure... 애노테이션을 조합해서 사용할 수 있습니다.

#### 자동 구성된 JSON 테스트

객체의 JSON 직렬화 및 역직렬화가 기대대로 동작하는지 테스트하려면 @JsonTest 애노테이션을 사용할 수 있습니다. 이 애노테이션은 다음 중 사용 가능한 JSON 매퍼를 자동 구성합니다:

- Jackson의 ObjectMapper, @JsonComponent 빈, Jackson Module
- Gson
- Jsonb

@JsonTest로 활성화되는 자동 구성 목록은 부록에서 확인할 수 있습니다.

자동 구성 요소를 세부적으로 설정하려면 @AutoConfigureJsonTesters 애노테이션을 사용할 수 있습니다.

Spring Boot는 JSONAssert 및 JsonPath 라이브러리와 함께 사용할 수 있는 AssertJ 기반 헬퍼들을 제공합니다. JacksonTester, GsonTester, JsonbTester, BasicJsonTester 클래스는 각각 Jackson, Gson, Jsonb, 문자열에 사용할 수 있으며, @JsonTest를 사용할 경우 필드 주입(@Autowired)이 가능합니다.

예시:

```java
@JsonTest
class MyJsonTests {

    @Autowired
    private JacksonTester<VehicleDetails> json;

    @Test
    void serialize() throws Exception {
        VehicleDetails details = new VehicleDetails("Honda", "Civic");
        assertThat(this.json.write(details)).isEqualToJson("expected.json");
        assertThat(this.json.write(details)).hasJsonPathStringValue("@.make");
        assertThat(this.json.write(details)).extractingJsonPathStringValue("@.make").isEqualTo("Honda");
    }

    @Test
    void deserialize() throws Exception {
        String content = "{\"make\":\"Ford\",\"model\":\"Focus\"}";
        assertThat(this.json.parse(content)).isEqualTo(new VehicleDetails("Ford", "Focus"));
        assertThat(this.json.parseObject(content).getMake()).isEqualTo("Ford");
    }
}
```

이러한 JSON 헬퍼 클래스는 일반 단위 테스트에서도 사용할 수 있으며, @JsonTest를 사용하지 않는 경우 @BeforeEach 메서드에서 initFields()를 호출해 초기화해야 합니다.

숫자 값을 JSON Path로 검증할 때, 타입에 따라 isEqualTo 대신 AssertJ의 satisfies를 사용할 수 있습니다. 예시:

```java
@Test
void someTest() throws Exception {
    SomeObject value = new SomeObject(0.152f);
    assertThat(this.json.write(value)).extractingJsonPathNumberValue("@.test.numberValue")
        .satisfies((number) -> assertThat(number.floatValue()).isCloseTo(0.15f, within(0.01f)));
}
```

#### Auto-Configured Spring MVC Tests

Spring MVC 컨트롤러가 올바르게 동작하는지 테스트하려면 @WebMvcTest 애노테이션을 사용하세요.
@WebMvcTest는 Spring MVC 인프라를 자동 구성하고, 스캔되는 빈을 다음과 같이 제한합니다:

- @Controller
- @ControllerAdvice
- @JsonComponent
- Converter, GenericConverter
- Filter, HandlerInterceptor
- WebMvcConfigurer, WebMvcRegistrations
- HandlerMethodArgumentResolver

@Component 및 @ConfigurationProperties 빈은 기본적으로 스캔되지 않습니다. @EnableConfigurationProperties를 사용하면 @ConfigurationProperties 빈을 포함시킬 수 있습니다.

@WebMvcTest에 의해 활성화되는 자동 구성 목록은 부록에서 확인할 수 있습니다.

필요한 컴포넌트(예: Jackson Module)를 추가하려면 @Import 애노테이션을 사용하여 설정 클래스를 가져올 수 있습니다.

보통 @WebMvcTest는 단일 컨트롤러에 대해 제한적으로 사용되며, 협력 객체에 대해 @MockitoBean을 조합해 모의 구현(mock)을 주입합니다.

#### MockMvc 자동 구성

@WebMvcTest는 MockMvc도 자동으로 구성합니다.
MockMvc는 전체 HTTP 서버를 시작하지 않고도 MVC 컨트롤러를 빠르게 테스트할 수 있는 강력한 방법을 제공합니다.

AssertJ가 클래스패스에 있으면, MockMvcTester를 통한 AssertJ 지원도 자동 설정됩니다.

@WebMvcTest 외에 (@SpringBootTest 등)에서도 @AutoConfigureMockMvc를 사용하면 MockMvc 및 MockMvcTester를 자동 구성할 수 있습니다.

예제:

```java
@WebMvcTest(UserVehicleController.class)
class MyControllerTests {

    @Autowired
    private MockMvcTester mvc;

    @MockitoBean
    private UserVehicleService userVehicleService;

    @Test
    void testExample() {
        given(this.userVehicleService.getVehicleDetails("sboot"))
            .willReturn(new VehicleDetails("Honda", "Civic"));
        
        assertThat(this.mvc.get().uri("/sboot/vehicle").accept(MediaType.TEXT_PLAIN))
            .hasStatusOk()
            .hasBodyTextEqualTo("Honda Civic");
    }
}
```

자동 구성 설정을 조정해야 한다면 (예: 서블릿 필터 적용 여부 등), @AutoConfigureMockMvc 애노테이션의 속성을 사용할 수 있습니다.

⸻

HtmlUnit 및 Selenium 사용하기

HtmlUnit 또는 Selenium을 사용하는 경우, 자동 구성은 HtmlUnit WebClient 빈 및/또는 Selenium WebDriver 빈도 제공합니다.

예제 (HtmlUnit 사용):

```java
@WebMvcTest(UserVehicleController.class)
class MyHtmlUnitTests {

    @Autowired
    private WebClient webClient;

    @MockitoBean
    private UserVehicleService userVehicleService;

    @Test
    void testExample() throws Exception {
        given(this.userVehicleService.getVehicleDetails("sboot"))
            .willReturn(new VehicleDetails("Honda", "Civic"));
        
        HtmlPage page = this.webClient.getPage("/sboot/vehicle.html");
        assertThat(page.getBody().getTextContent()).isEqualTo("Honda Civic");
    }
}
```

기본적으로 Spring Boot는 각 테스트 후 드라이버가 종료되고 새 인스턴스가 주입되도록 WebDriver 빈에 특별한 “scope”을 설정합니다.
이러한 동작을 원하지 않는다면 @Bean 정의에 @Scope(ConfigurableBeanFactory.SCOPE_SINGLETON)을 명시하여 전역 싱글톤으로 설정할 수 있습니다.

주의: Spring Boot가 생성한 webDriver 스코프는 동일한 이름의 사용자 정의 스코프를 대체합니다. 따라서 @WebMvcTest를 사용할 경우 사용자 정의 webDriver 스코프가 제대로 작동하지 않을 수 있습니다.

#### Spring Security와의 통합

클래스패스에 Spring Security가 있다면, @WebMvcTest는 WebSecurityConfigurer 빈도 스캔합니다.
보안을 테스트에서 완전히 비활성화하기보다는 Spring Security의 테스트 지원을 활용하는 것이 좋습니다.

자세한 내용은 Spring Security 테스트 가이드의 “How-to Guides” 섹션을 참고하세요.

실제 서버를 이용한 전체 테스트

경우에 따라 MVC 테스트만으로는 충분하지 않을 수 있습니다.
Spring Boot는 실제 서버를 포함한 엔드 투 엔드 테스트를 실행하는 데에도 도움을 줍니다.
